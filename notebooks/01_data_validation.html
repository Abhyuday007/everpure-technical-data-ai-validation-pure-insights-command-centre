Case Study 3: Data Validation Notebook¶

Pure Insights Command Centre: Report Monitoring Dataset

I started by checking the dataset before using it in the dashboard or cost calculations. The aim here is to identify the data-quality problems, decide how to handle them, and document any assumptions I have to make.

This notebook produces two outputs:

  • data/pure_insights_clean.csv — the cleaned dataset used by the application and SQL analysis
  • data/dq_issues.csv — a log of the data-quality issues found during validation

Where possible, I have kept the original rows and added flags instead of deleting records. For example, if a row has invalid Snowflake credits, the credit value is excluded from cost calculations but the rest of the report information is retained.

The cleaning rules are kept in validation/cleaning.py so that the notebook and backend use the same logic.

Repeated report IDs¶

One important thing I noticed is that the 2,000 rows do not represent 2,000 unique reports. There are 100 unique report_id values, with each report appearing exactly 20 times.

I checked whether these were simple duplicate rows, but they are not. Values change between occurrences of the same report, including the owner field.

The dataset does not include a timestamp, so I cannot confirm the actual chronological order of these records. For this analysis, I treat the repeated rows as report snapshots and use their original file order to create snapshot_seq from 1 to 20.

This is an assumption rather than something the dataset proves, so I keep it explicit. If timestamped source data were available, I would use that instead.

Because ownership can change between snapshots, orphan status is evaluated at the snapshot level. I also calculate how often each report appears without an owner.

Orphaned reports¶

Missing ownership appears in two forms in the dataset: 'nan' and 'ORPHANED_REPORT'.

Checking only one of these would miss part of the problem, so I map both to a single is_orphaned flag. I also keep an orphan_reason field so I can still distinguish how the missing owner was represented in the original data.

Negative Snowflake credits¶

The dataset contains negative values for snowflake_credits_consumed. These should not be used directly in the cost calculation.

Rather than converting them to positive values or trying to guess a replacement, I set the corresponding credits_clean value to null. This keeps the rest of the row available for analysis while preventing an invalid credit value from affecting cost totals.

I also flag these rows separately so the issue remains visible in the data-quality output.

Load latency and alert thresholds¶

The case study specifies an alert when load latency exceeds 15 seconds. In this dataset, however, a large proportion of observations cross that threshold.

I keep the required 15-second threshold, but treat it as a warning. I added a second threshold at 30 seconds for critical alerts so that the more severe cases are easier to identify.

The 30-second threshold is my design choice rather than something specified in the case study. It is configurable in the application.

The backend also applies a per-report cooldown to avoid repeatedly sending the same alert while a report remains slow.

Relationships between usage and cost¶

I also checked whether the main usage, performance and cost variables move together.

The correlations are generally very weak. For example, higher report views are not strongly associated with higher AWS cost, and higher query counts are not strongly associated with higher Snowflake credits in this dataset.

Because of this, I do not use these relationships to make claims such as "more heavily used reports always cost more" or "slower reports consume more credits." The data does not support those conclusions.

Instead, I use metrics such as cost per view as descriptive indicators. These can help identify reports worth investigating, but they should not be interpreted as evidence that usage itself caused the cost.

Additional validation checks¶

I found a few other cases that need explicit handling:

  • UNKNOWN refresh status (100 rows): I keep this as a separate state rather than treating it as either a successful or failed refresh. It therefore does not trigger a refresh-failure alert.
  • Zero views (4 rows): cost-per-view cannot be calculated for these observations, so the resulting metric is left as NULL.
  • Peak concurrent users above monthly views (93 rows): these observations are internally inconsistent because peak concurrent users exceed the reported monthly views. I flag them for review but do not modify the original values.

Current orphan status¶

No report is orphaned across all 20 observations. Some reports, however, are missing an owner in a substantial share of their snapshots.

For the dashboard, I define a report as currently orphaned when the last available snapshot for that report has no valid owner.

Since the dataset has no timestamp, "last" here means the highest snapshot_seq based on file order. This should be replaced by timestamp ordering if the production source provides one.

Summary of validation decisions¶

Issue Treatment
Repeated report_id Keep the rows and treat them as snapshots using snapshot_seq. This is based on file order because no timestamp is provided.
Missing report owners Map both 'nan' and 'ORPHANED_REPORT' to is_orphaned while retaining the original reason.
Negative Snowflake credits Flag the observation and set credits_clean to null for cost calculations.
UNKNOWN refresh status Keep it as a separate state rather than interpreting it as success or failure.
High load latency Keep the required >15s alert threshold as a warning and use >30s as an additional critical tier.
Repeated latency alerts Apply a per-report cooldown in the backend to reduce duplicate notifications.
Zero report views Return NULL for per-view metrics rather than dividing by zero.
Usage/cost relationships Use cost-per-view and similar metrics descriptively rather than making causal claims from weak correlations.

The cleaned dataset is written to data/pure_insights_clean.csv, and all detected validation issues are written to data/dq_issues.csv.

The SQL cost-allocation workflow uses credits_clean rather than the original Snowflake credit field, and the backend reads the same cleaned dataset. This keeps the validation rules consistent across the analysis and application.
